From themes to a component tree

Next.js and TypeScript, walked through the Acme dashboard. For people who already ship WordPress, and for people who already know React.

Arrows move N notes G overview F full screen
Open on the Acme home page in another window. Say who the hour is for: WordPress people do not need React 101, and React people do not need “what is a component.” The new part is where rendering, routing, and data meet.

01 · Frame

Three questions for the hour

What carries

Templates, URLs, auth gates, validation, and cache busting. You have already solved these. The names change.

What is new

The server renders React by default. Some components never become JavaScript. Mutations are functions, not a new endpoint.

What to unlearn

One PHP template per request. Enqueue everything. Fetch from the client because that is where you are used to putting behavior.

Specimen: this repo, the finished Next.js Learn dashboard. Code citations open the file in the editor.

Promise a practical comparison, not a framework tour. If time gets short, keep slides 4, 5, 7, 11, 15, and 20. Those are the argument.

02 · Specimen

Acme is a small admin, on purpose

Public

app/page.tsx marketing home.

app/login/page.tsx credentials form.

Private, under /dashboard

Overview, invoices, create, edit, customers. Shared chrome in one layout. Postgres behind app/lib/data.ts.

Treat it as a custom post type called Invoice, with a list table, an edit screen, and a front page. The interesting part is that none of those are plugins.

Click around for 20 seconds if the app is running: home, login, invoices search. Point out there is no wp-admin. The product UI and the “admin” are the same React tree.

04 · Where the habit breaks

Four places a WordPress reflex fights you

There is no theme

Routing is the filesystem under app/. Adding a screen is adding a folder, not registering a page template.

The default render is the server

A component can await the database and ship HTML only. 'use client' is the exception you opt into.

Do not invent an AJAX route first

A form can call a server function. A new REST route is a choice, not the starting move.

Logged-in is not allowed

You already know is_user_logged_in() versus current_user_can(). The edge check does not replace the action check.

This is the slide to linger on. The rest of the deck is evidence for these four. If someone says “so it’s just headless WordPress,” come back here: there is no posts table, no template hierarchy, and no admin-ajax unless you build them.

05 · Project structure

Same jobs, different drawers

A theme you know

theme/ style.css functions.php header.php footer.php front-page.php page-invoices.php template-parts/ inc/queries.php assets/

This repo

app/ layout.tsx root chrome page.tsx / login/page.tsx dashboard/ layout.tsx sidebar (overview)/page.tsx invoices/page.tsx lib/ queries, types, actions ui/ components proxy.ts request gate auth.ts

app/ui is colocation, like template-parts, but it is not a route. Only page.tsx, layout.tsx, route.ts, and a few siblings become URLs.

Stress the parenthesis folder (overview): it groups the dashboard home without adding a URL segment. That is a route group. WordPress has no equivalent; the closest feeling is a template that does not get its own slug.

08 · The client boundary

Active menu state is the part that needs the browser

'use client';

export default function NavLinks() {
  const pathname = usePathname();
  return links.map((link) => (
    <Link
      href={link.href}
      className={clsx(/* ... */, {
        'bg-sky-100 text-blue-600':
          pathname === link.href,
      })}
    />
  ));
}
app/ui/dashboard/nav-links.tsx:1-48

WordPress did this in PHP

current_page_item is computed while rendering the menu. That still works on the server.

This file is a client component because usePathname() subscribes to client navigations. The sidebar around it stays a server component.

SideNav even posts sign-out as an inline server action. Server shell, client island, server function, one file apart.

app/ui/dashboard/sidenav.tsx:21-25
This is the intermediate point React-familiar people still miss. 'use client' does not mean “this runs only in the browser.” It means “this module may use state and effects, and its JS is shipped.” The parent server component can render it. You cannot import a server component into this file.

09 · TypeScript

The type is the schema you used to keep in comments

export type Invoice = {
  id: string;
  customer_id: string;
  amount: number;
  date: string;
  status: 'pending' | 'paid';
};

export type LatestInvoiceRaw =
  Omit<LatestInvoice, 'amount'> & {
    amount: number;
  };
app/lib/definitions.ts:19-45

Why the second type exists

  • The database stores cents as a number.
  • The card shows a formatted string.
  • Omit plus an intersection is the boundary between those two shapes.

A union on status is the compile-time version of “this meta value may only be pending or paid.” PHP would discover the typo at runtime.

For the TypeScript-fluent people: these types are hand-written for the course. Say that Prisma or Drizzle would generate them, the way register_post_type does not generate a type but an ORM can. For WordPress people: compare with trusting get_post_meta to return a string.

10 · React, the new default

Async components are allowed. That is the shift.

export default async function CardWrapper() {
  const {
    numberOfInvoices,
    numberOfCustomers,
    totalPaidInvoices,
    totalPendingInvoices,
  } = await fetchCardData();

  return (
    <>
      <Card title="Collected" value={totalPaidInvoices} />
      {/* ... */}
    </>
  );
}
app/ui/dashboard/cards.tsx:17-23

Map it to PHP, carefully

It feels like a template that calls WP_Query and prints markup. The difference: the result is a React tree, and the client does not receive fetchCardData.

No useEffect. No loading flag inside the card. If you reach for those on first read of server data, you are porting a client habit into a server job.

People who know React from 2019 will try to fix this with useEffect. Stop them kindly. Data for the first paint belongs in the async server component. Client state is for things the server cannot know: the current pathname, an open dialog, a debounced keystroke.

11 · Data

Queries live in one module, like inc/queries.php

const invoiceCountPromise = sql`SELECT COUNT(*) FROM invoices`;
const customerCountPromise = sql`SELECT COUNT(*) FROM customers`;
const invoiceStatusPromise = sql`
  SELECT SUM(CASE WHEN status = 'paid'
    THEN amount ELSE 0 END) AS "paid",
    /* pending too */
  FROM invoices`;

const data = await Promise.all([
  invoiceCountPromise,
  customerCountPromise,
  invoiceStatusPromise,
]);
app/lib/data.ts:51-67

Practical differences

  • There is no WP_Query. SQL is visible. Tagged templates pass values as parameters.
  • Promise.all is the parallel version of three queries you would otherwise run in sequence.
  • The list table is also a server component. It receives query and currentPage as props and awaits inside.
app/ui/invoices/table.tsx:7-14
Mention SQL injection briefly: the sql tag from postgres.js parameterizes interpolated values. That is the analogue of $wpdb->prepare. Do not build the query with string concatenation. The connection helper is app/lib/postgres.ts.

13 · Search and pagination

Search belongs in the URL, the way query vars did

'use client';

const handleSearch = useDebouncedCallback((term) => {
  const params = new URLSearchParams(searchParams);
  params.set('page', '1');
  if (term) params.set('query', term);
  else params.delete('query');
  replace(`${pathname}?${params.toString()}`);
}, 300);
app/ui/search.tsx:12-24 
export default async function Page(props: {
  searchParams?: Promise<{
    query?: string;
    page?: string;
  }>;
}) {
  const searchParams = await props.searchParams;
  const query = searchParams?.query || '';
  const currentPage = Number(searchParams?.page) || 1;
  const totalPages = await fetchInvoicesPages(query);
}
app/dashboard/invoices/page.tsx:15-25

The client writes the query string. The server reads it and queries Postgres. Shareable URLs, back button, and no duplicated React state. In current Next.js, searchParams is a Promise. You await it.

This split is the whole architecture in one feature. WordPress people: this is ?s= and paged, with pre_get_posts on the server. React people: resist storing the search string in useState as the source of truth. Debounce is the only client behavior required.

14 · Mutations

A form action can be a function on the server

'use server';

export async function createInvoice(prevState, formData) {
  const validatedFields = CreateInvoice.safeParse({
    customerId: formData.get('customerId'),
    amount: formData.get('amount'),
    status: formData.get('status'),
  });
  if (!validatedFields.success) {
    return { errors: /* field errors */, message: '...' };
  }
  await sql`INSERT INTO invoices ...`;
  revalidatePath('/dashboard/invoices');
  redirect('/dashboard/invoices');
}
app/lib/actions.ts:36-72

WordPress equivalents

  • admin-post.php plus a hooked callback.
  • A REST POST you registered in functions.php.
  • wp_insert_post, then wp_safe_redirect.

Delete is the small version: bind the id, put the function on <form action>.

app/ui/invoices/buttons.tsx:28-37
Login uses the same pattern with useActionState so the server can return “Invalid credentials.” without a hand-rolled fetch. Cite login-form.tsx lines 18-24. Progressive enhancement: the form still posts if you think of it as HTML first.

15 · Mutations

Zod is sanitize_* with a return type

const FormSchema = z.object({
  customerId: z.string({
    invalid_type_error: 'Please select a customer.',
  }),
  amount: z.coerce.number()
    .gt(0, { message: 'Please enter an amount greater than $0.' }),
  status: z.enum(['pending', 'paid'], {
    invalid_type_error: 'Please select an invoice status.',
  }),
});

const CreateInvoice = FormSchema.omit({ id: true, date: true });
app/lib/actions.ts:10-24

What the room should copy

  • safeParse returns errors. It does not throw on bad input.
  • The action returns { errors, message } and the form renders them. That is the admin notice, field by field.
  • The union 'pending' | 'paid' shows up again. The type and the validator match.
  • Amount is coerced from the form string, then stored as cents.
WordPress habit: sanitize on the way in, escape on the way out. Keep that. Zod replaces the ad-hoc sanitize for structured input. Escaping on the way out is mostly React’s text rendering, plus next/image for the customer portraits. Nonces: server actions have a framework-level action id. You still need authorization, next slide.

16 · Auth

The gate is a proxy. The check still belongs in the action.

callbacks: {
  authorized({ auth, request: { nextUrl } }) {
    const isLoggedIn = !!auth?.user;
    const isOnDashboard =
      nextUrl.pathname.startsWith('/dashboard');
    if (isOnDashboard) return isLoggedIn;
    if (isLoggedIn)
      return Response.redirect(new URL('/dashboard', nextUrl));
    return true;
  },
}
auth.config.ts:12-22 proxy.ts:1-9

Two files, on purpose

auth.config.ts is safe to import from the proxy. auth.ts uses bcrypt and Postgres, which the proxy runtime cannot.

That split is in the comment at the top of the config. It is the same instinct as keeping heavy hooks out of a must-use plugin that runs everywhere.

auth.config.ts:7-9 auth.ts:9-16
Advanced caveat, say it: deleteInvoice does not call auth() itself. The proxy covers dashboard navigations, including server-action posts to those URLs, but “is logged in” is the only rule. One user in the seed makes that invisible. In production, check the user inside the action the way an AJAX callback calls current_user_can.

17 · Cache

Write, then say which screen is stale

WordPress

  • A transient keyed by the query.
  • save_post deletes that key.
  • Forget the delete and the list lies until expiry.

This app

  • After insert, update, or delete: revalidatePath('/dashboard/invoices').
  • Then redirect back to the list, so the next render reads Postgres again.
  • Reads here are SQL on each request. The call still matters so the client router does not reuse the old list.
app/lib/actions.ts:71-72 and 110-113

The skill that transfers is knowing invalidation is part of the write. The new part is that Next has more than one cache, and this sample only touches the path you just mutated.

Do not teach the full cache matrix unless asked. If an advanced person asks: Full Route Cache, Data Cache, Router Cache. This sample is dynamic because of search params and uncached SQL. revalidatePath is still the explicit “this list changed.” Point them at the Next.js caching docs rather than improvising.

21 · For people who already learned Next.js

A few things moved since the tutorial you remember

App Router

This project has no pages/ router. Layouts, loading, and server components are the model.

Async request data

searchParams and params are Promises. The invoices page and the edit page both await them.

proxy.ts

Next.js 16 runs this file where older docs say middleware.ts. Same job: run before the route.

Also in this stack: React 19 useActionState, server actions, and Auth.js v5 split so the proxy stays free of Node-only code. None of that is required to understand components. All of it shows up in this repo.

If the room learned the Pages router, do not re-teach it. Tell them the mental model that changed is “data fetching moved into server components” and “middleware was renamed proxy in v16.” Version in this repo is Next 16.3. Offer the docs rather than a migration guide unless they ask.

23 · Leave time for this

Worth arguing about

With the WordPress side

  • Which of our plugins are really “a route, a query, and a form”?
  • Where do we still want an editorial admin that Next does not give us?
  • What would we miss from hooks if the filesystem is the only extension point?

With the React side

  • Which screens in our apps are still client-fetched out of habit?
  • Are we authorizing inside actions, or only at the proxy?
  • Do our types describe the database row, or the formatted view?
